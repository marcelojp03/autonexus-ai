# CU15 — Eventos v1, Outbox e Inbox

Estado: contrato aprobado para implementar, sin publicación/consumidores acreditados todavía. Vinculado a contracts/rest/saga.md y docs/compose/spec/cu15-confirmation-saga.md.

## Envelope

Campos obligatorios: eventId UUID estable; schemaVersion=1; eventType de la lista cerrada; producer; aggregateType/aggregateId/aggregateVersion; sagaId como correlationId; causationId del comando/paso; occurredAt UTC; initiatedBy y executedBy sin token; data con referencias y estados mínimos. Tope de mensaje 64 KiB, sin datos personales, credenciales, imágenes ni instrucciones ejecutables.

| Producer | eventType/routing key | Datos mínimos |
| --- | --- | --- |
| operations | operations.cu15.confirmation.updated.v1 | sagaId, orderId, status, phase, stepId, versión |
| operations | operations.cu15.confirmation.rejected.v1 | sagaId, orderId, motivo saneado; compensaciones terminadas |
| operations | operations.order.confirmed.v1 | sagaId, orderId, assignmentId, employeeId, startsAt/endsAt, quoteId/quoteVersion, quoteLinkId |
| employees | employees.cu15.assignment.reserved.v1 | sagaId, assignmentId, orderId, employeeId, intervalo, status/version |
| employees | employees.cu15.assignment.confirmed.v1 | Las mismas referencias, status/version confirmados |
| employees | employees.cu15.assignment.released.v1 | Las mismas referencias, status/version y motivo tipado |
| employees | employees.cu15.command.rejected.v1 | sagaId, operationId, command y errorCode saneado; sin efecto de asignación |
| finance | finance.cu15.quote_link.authorized.v1 | sagaId, quoteLinkId, orderId, quoteId/quoteVersion, status/version |
| finance | finance.cu15.quote_link.cancelled.v1 | Las mismas referencias, status/version y motivo tipado |
| finance | finance.cu15.command.rejected.v1 | sagaId, operationId, command y errorCode saneado; sin crear vínculo |

El eventId no cambia por un reintento del publicador. Un cambio posterior del agregado produce un evento nuevo con otra versión; no se reutiliza un ID con distinto cuerpo. Ningún consumidor deduce autoridad de textos, notas o del nombre de un rol dentro del payload.

## Commit y publicación

Cada propietario guarda cambio + ledger idempotente + auditoría + Outbox en una transacción PostgreSQL propia. Outbox conserva envelope, intentos, próxima ejecución, lease/fencing y publishedAt. No se publica dentro de la transacción de negocio ni se marca publicado antes de la confirmación.

RabbitMQ: exchange topic durable autonexus.business.v1, colas/bindings durables creados antes de habilitar publicadores y mensajes persistentes. Publisher confirms + mandatory con handler de basic.return: un mensaje devuelto/no enrutable sigue pendiente aunque llegue ACK del broker. NACK, conexión perdida o confirmación no recibida conservan/reintentan el mismo evento.

Si se publicó pero se perdió el marcado SQL, se puede volver a publicar: semántica al menos una vez, no exactamente una entrega. La indisponibilidad de RabbitMQ no convierte un commit SQL confirmado en rechazo de negocio.

## Consumo

- Operaciones recibe eventos de participantes para registrar recibo/despertar conciliación de una Saga propia. El worker consulta el resultado autorizado del comando; el mensaje por sí solo no confirma la orden.
- Empleados recibe operations.order.confirmed.v1, verifica referencias de su asignación/Saga y registra notificación durable y marca de cierre global en la misma transacción de Inbox. Hasta observarlo no se permite que un cambio CU04 invalide la asignación de una Saga aún pendiente, aunque el paso E ya diga confirmed. No crea una segunda asignación ni acredita lectura humana o CU05.
- Todo consumidor valida esquema/tipo/productor/referencias y guarda Inbox UNIQUE(eventId) + huella + efecto/proyección local en una misma transacción; ACK solo después del commit. Duplicado idéntico: ACK sin repetir efecto. Igual eventId/cuerpo diferente: conflicto y cuarentena, nunca sobrescribir.
- No se usa únicamente redelivered para deduplicar: el publicador también puede duplicar como entrega nueva. Pérdida de ACK tras commit provoca redelivery segura por Inbox.
- Mensaje inválido/conflictivo: DLQ/cuarentena con razón saneada, sin bucle de requeue ni ejecutar comandos del texto. No se elimina historia para poder reprocesar un duplicado.

Credenciales privadas por productor/consumidor y permisos de vhost/topic/colas acotados; ningún cliente web tiene acceso al broker. Publicadores/consumidores se implementan como adaptadores de infraestructura en cada propietario; no existe un dominio compartido entre servicios.

## Verificación exigida

Broker real y tres bases: filas Outbox junto al commit, confirm y publishedAt, retransmisión tras publicación sin marcado, dos publicaciones del mismo eventId con un solo efecto Inbox/notificación, y recuperación tras caída/reinicio. Cada fallo introducido se identifica como inyectado. No basta un mock de EventPublisher ni contar mensajes enviados por una API.

Fuentes técnicas contrastadas: https://www.rabbitmq.com/docs/publishers, https://www.rabbitmq.com/docs/confirms y https://www.rabbitmq.com/docs/reliability. Versiones de broker y bibliotecas se fijan después de comprobar compatibilidad al implementar.
