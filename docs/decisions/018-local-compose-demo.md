# 018 — Entorno integrado local, configuración privada y demo conservadora

Fecha: 2026-10-29. Diseño aprobado en local-compose-demo; implementación/verificación en work/marcelo. El estado de cierre y publicación se registra en STATUS, no se infiere de esta decisión.

## Contexto

El conjunto implementado dependía de runtimes y builds del host, y usaba entornos locales separados. El usuario pidió una entrada Docker Compose reproducible, un README público y datos sintéticos relacionados mediante la Saga real, conservando los entornos/credenciales/volúmenes anteriores. El modo web de esta entrega es integrado y online.

## Decisiones

1. Compose raíz con redes/volúmenes por proyecto, sin container_name ni volúmenes globales fijos. Solo la web se publica por loopback. PostgreSQL de aplicaciones e IdP, broker, APIs, administración y workers quedan internos. No se agregan servicios aparentes de Inteligencia/Sincronización/MCP ni se acredita el resto del parcial.
2. Builds multietapa desde fuentes y lockfiles, con versiones e imágenes fijadas por digest. Node22.22.3/pnpm12.6.0, Maven Wrapper/Java21 y PHP8.4.26: el composer.lock existente requiere PHP≥8.4.1. Las dos aplicaciones Angular, React y Shell se compilan dentro de Docker. Los consumidores finales no contienen dependencias/builds del host ni secretos. Nginx corre sin root en8080; su configuración y permisos de temporales se verifican durante el build.
3. Un único origen público, Keycloak bajo /identity y GraphQL bajo /graphql. El issuer público permanece exacto al verificar JWT; JWKS, administración IdP y client_credentials pueden usar URLs internas confiables independientes. No se toman endpoints de claims ni se deshabilitan firma, audiencia, vigencia o hostname para resolver DNS. Defaults locales anteriores conservados; los binds de contenedor son explícitos.
4. Configuración pública runtime del Shell con esquema cerrado y mismo origen: OIDC, GraphQL y los cuatro diagnósticos CU01. No incluye secretos. El bearer sigue solo en RAM y SessionPort es el único transporte empresarial web. Los microfrontends integrados no instancian otro SDK ni reciben tokens.
5. Bootstrap genera secretos una vez en un volumen canónico privado y distribuye solo la configuración de cada consumidor en su volumen. Web/BFF no reciben SQL, broker ni administración IdP. Los clientes de administración Empleados y coordinación CU15 son distintos; el coordinador conserva siete scopes de participantes y solo audiencias E/F, sin realm-management. El scope interno service_account que Keycloak26.8 añade automáticamente no es un permiso empresarial ni se habilita en el navegador.
6. El cliente público conserva fullScopeAllowed del entorno anterior para que los roles personalizados de CU02 puedan emitirse. Esos roles son metadatos de identidad, no permisos: Empleados los cruza con catálogo/asignaciones/vínculo vigente y cada propietario autoriza la operación/registro. Los clientes técnicos permanecen restringidos; ningún scope técnico se publica como scope opcional/default del Shell.
7. La provisión inicial puede reconciliar únicamente los cuatro permisos de cuenta predeterminados conocidos de Keycloak. Una marca durable de finalización hace que una deriva posterior falle sin sobrescribirse. Se preservan contraseñas/client secrets. Las migraciones pertenecen a cada servicio; no se usa synchronize, reset ni down -v. Una corrección de transporte de Finanzas añade su URL interna de permisos solo al predecesor generado exacto, atómicamente y sin cambiar credenciales; cualquier otra edición falla por conflicto.
8. Bootstrap/migraciones, demo y fixtures de aceptación son procesos separados. Demo requiere perfil/flag explícitos, usa APIs y CU15 real, guarda comandos/operationIds/IDs antes de los efectos y conserva un ledger privado. Fecha civil de La Paz congelada en preparación, sin retiming silencioso. Credenciales solo se preparan para nuevas identidades propias; ante incertidumbre se prueba la credencial existente, nunca se restablece automáticamente. flock impide runners simultáneos sobre el mismo ledger.
9. Las pruebas de aceptación usan otro proyecto Compose y una copia Git sin .git, dependencias, builds ni secretos del host. El browser opcional corre también en Docker; un relay TCP de prueba permite alcanzar el origen loopback exacto desde ese contenedor, sin reescribir HTTP, falsificar respuestas ni omitir autenticación. No se monta Docker socket. El control de caídas/reinicios queda en el supervisor del operador y valida proyecto, servicio y directorio antes de tocar un contenedor.
10. PostgreSQL remoto se parametriza por propietario con verify-full y CA explícita cuando corresponda. Atlas/DynamoDB son preparación documental de servicios futuros, no conexiones implementadas. AWS/Azure/GCP se comparan como propuesta: portabilidad OCI/protocolos no equivale a multinube operativa. No se contratan ni despliegan recursos remotos.

## Consecuencias y límites

El primer build necesita red para imágenes y paquetes; las mediciones distinguen fallos iniciales, caché e iteraciones corregidas. Un healthcheck SQL no demuestra entrega de eventos ni una confirmación distribuida. La aceptación debe comprobar Saga, Outbox/Inbox, repetición, edición conservada, reinicio y recuperación reales.

El servidor PHP de desarrollo y Keycloak start-dev son locales; no certifican producción/HA. Los roles o datos del demo no son identidades reales de integrantes/clientes. Se conservan artefactos fallidos y se distingue prueba sintética, compilación e integración real. La revisión visual de CU05 tiene su propio estado y no se acredita desde texto de una herramienta de imágenes.
